# Architecture Decision Records (ADR) — GhostVPN

В этом документе зафиксированы ключевые архитектурные решения для обеспечения стабильной работы коммерческого VPN-бота на инфраструктуре **Render Free (512 MB RAM)** + **Neon/Supabase PostgreSQL** + **3X-UI v3.11.0**.

---

## ADR-001: Единый процесс FastAPI + Aiogram Webhook + APScheduler без Docker и Redis

### Контекст
Бесплатный тариф Render (Web Service) предоставляет 512 МБ оперативной памяти, эфемерную файловую систему и усыпляет сервис при отсутствии входящего HTTP-трафика в течение 15 минут. Запуск отдельных воркеров (Celery + Redis) потребует дополнительных платных инстансов и превысит лимит RAM.

### Решение
1. Использовать нативный Python-рантайм Render (`render.yaml` + `requirements.txt`) со стартом ровно одного воркера: `uvicorn main:app --host 0.0.0.0 --port $PORT --workers 1`.
2. Объединить в одном event loop (`asyncio`):
   - **FastAPI** (обработка вебхуков Telegram, платёжных шлюзов, редиректов для VPN-приложений и эндпоинтов `/health`, `/ping` для анти-сна);
   - **Aiogram 3.x** в режиме Webhook (`SimpleRequestHandler` / FastAPI route);
   - **APScheduler (`AsyncIOScheduler`)** для фоновых задач (проверка истекающих подписок и докачка зависших выдач 3X-UI).
3. Генерацию QR-кодов выполнять строго в оперативной памяти (`io.BytesIO` + `BufferedInputFile`) без записи на эфемерный диск.

### Последствия
- Потребление RAM составляет ~85–110 МБ, что в 4.5 раза ниже лимита Render Free (512 МБ).
- Внешний бесплатный пингер (UptimeRobot / Cron-job.org), стучащийся каждые 10 минут в `GET /ping`, поддерживает контейнер и пул соединений БД в активном состоянии 24/7.

## ADR-002: Работа с облачной PostgreSQL (Neon / Supabase) через PgBouncer и Cold Start Retry

### Контекст
Облачные провайдеры PostgreSQL (Supabase Supavisor, Neon Connection Pooler) используют PgBouncer в режиме `transaction` или `statement`, который не поддерживает prepared statements драйвера `asyncpg` по умолчанию. Кроме того, бесплатные БД Neon могут уходить в `scale-to-zero` (холодный старт занимает 500–1500 мс).

### Решение
1. Настроить `create_async_engine` с параметрами:
   - `pool_pre_ping=True` (проверка живости соединения перед выдачей из пула);
   - `pool_recycle=300` (переоткрытие соединений каждые 5 минут);
   - `pool_size=5, max_overflow=5` (экономия лимита коннектов бесплатной БД и RAM);
   - `connect_args={"statement_cache_size": 0}` (отключение кэша prepared statements для 100% совместимости с PgBouncer/Supavisor).
2. При старте приложения выполнять инициализацию БД и seed тарифов с экспоненциальным retry (до 5 попыток), чтобы пережить пробуждение БД.

## ADR-003: Защита фоновых задач от дублирования через PostgreSQL Advisory Locks

### Контекст
Во время деплоя новой версии на Render (Zero-Downtime Deploy) старый и новый контейнеры могут работать параллельно в течение 10–30 секунд. Если в этот момент сработает крон-задача в `APScheduler`, пользователи могут получить дублирующиеся уведомления, либо произойдёт гонка при обращении к API 3X-UI.

### Решение
1. Каждый запуск периодической задачи оборачивается в сессионный неблокирующий PostgreSQL Advisory Lock: `SELECT pg_try_advisory_lock(:lock_id)`. Если блокировка уже удерживается другим инстансом, задача немедленно завершается.
2. Дополнительно в таблице `subscriptions` хранятся идемпотентные флаги `notified_3d`, `notified_1d`, `notified_expired`, которые обновляются атомарно и сбрасываются при продлении подписки.

## ADR-004: Отказоустойчивый биллинг и статус `PAID_PENDING_PROVISION` (Outbox Pattern)

### Контекст
Пользователь может оплатить подписку (через Telegram Stars или CryptoBot), но в момент прихода вебхука VPS-сервер с панелью 3X-UI может перезагружаться или испытывать кратковременную сетевую недоступность. Потеря оплаты недопустима.

### Решение
1. Обработка платежа разделена на две фазы:
   - **Фаза 1 (Фиксация оплаты в БД):** Атомарно проверяется статус транзакции (`PENDING`), начисляется реферальное вознаграждение (15%) рефереру, списывается использованный бонусный баланс и транзакция переводится в статус `PAID_PENDING_PROVISION`.
   - **Фаза 2 (Выдача в 3X-UI):** Выполняется вызов API 3X-UI (`addClient` / `updateClient`). При успехе транзакция переводится в `COMPLETED`, а подписка активируется.
2. Если Фаза 2 завершается ошибкой сети/API, пользователю отправляется сообщение: *«✅ Оплата получена! Сервер синхронизирует ваш ключ, доступ появится автоматически в течение пары минут»*, в админ-чат уходит критический алерт, а фоновый воркер `retry_pending_provisions` повторяет выдачу каждые 30 секунд до победного конца.

## ADR-005: Управление сессиями 3X-UI v3.11.0 и неизменность Subscription URL

### Контекст
Панель 3X-UI v3.11.0 использует cookie-авторизацию (`POST /login`, cookie `3x-ui` / `session`), которая со временем истекает. При вызове `addClient` и `updateClient` панель ожидает внутри JSON-тела вложенное поле `settings`, сериализованное как JSON-строка (`"{\"clients\": [...]}"`).

### Решение
1. `XUIClient` хранит `httpx.AsyncClient` с jar-хранилищем cookies и `asyncio.Lock` на авторизацию. При получении HTTP `401`/`403`/`404` или ответа `{"success": false}` с потерей сессии клиент автоматически выполняет повторный `login()` и прозрачно повторяет исходный запрос.
2. **Модель «1 пользователь = 1 клиент в 3X-UI»:** Клиент идентифицируется по `email = f"tg_{telegram_id}"`. При продлении (даже после истечения срока) обновляется существующий клиент (`updateClient/{uuid}`), что сохраняет его `subId` и избавляет пользователя от необходимости менять `Subscription URL` в приложениях Happ / v2rayTun / Hiddify.
